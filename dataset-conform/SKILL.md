# Dataset Conform

把一份规模较大的结构化数据集，按参考样例的格式与质量标准全量对齐。

数据领域无关：英语词根、题库、商品目录、知识卡片、法条摘要都适用。领域知识来自你读到的参考样例和规则文档，不来自本 skill。

## 核心思路

处理这类任务最容易踩的坑有三个，整套流程都是为了绕开它们：

1. **一次性把整份数据塞进上下文** —— 几 MB 的数据装不进来，也无法保证输出不丢条目。所以先用脚本做机械校验定位问题，再按条目分片，交给并行子代理修，最后脚本合并 + 完整性守卫。
2. **把「格式判断」交给模型** —— 字段是否缺失、数组数量是否与参考样例一样、索引是否越界，这些是确定性问题，脚本判断又快又准；模型只该处理需要语义判断的事（释义是否正确、翻译是否忠实、构词推导是否成立）。
3. **规格靠脑补** —— 必须先把格式契约显式提炼成一份机器可校验的 `spec.json` + 人可读的规则说明，再用参考样例校准：**样例报出 error 时，先判断是 spec 太严还是样例本身有缺陷**，两种都可能，判据见「常见坑」第一条。既有规则文档（如 `rule_description.md`）与参考样例都是规格来源，冲突时不要默认某一方胜出。


## 三种运行模式

先判断用户要哪一种，不确定就直接问：

- **audit（总结性体检）**：只出报告，不改数据。给出整份数据的质量画像：违反了哪些规则、各占多少条、典型样例、系统性问题归纳、修复优先级建议。
- **conform（全量对齐）**：体检 + 全量修复 + 补全，产出对齐后的完整数据集和变更报告。默认模式。
- **targeted（针对性补充）**：只处理限定范围——某类问题（如「只修 quiz 索引越界」）、某些字段（如「只补 examples[].image」）、或某批条目 id。范围之外的内容一个字都不许动。

三种模式共用 Step 1~2；audit 到 Step 3 结束；conform / targeted 走完全程。

## 工作区

所有中间产物放在数据文件同级的 `.dataset-conform/run-N/` 下（N 从 1 递增，便于多轮迭代对比）：

```
.dataset-conform/run-1/
├── spec.json          机器可校验的规格          （所有模式）
├── spec.md            人可读的规则说明（含语义规则）（所有模式）
├── audit.json         全量校验结果              （所有模式）
├── report.md          最终报告                  （所有模式）
├── shards/            待修分片（脚本生成）        （conform / targeted）
├── fixed/             子代理写回的修复分片        （conform / targeted）
└── merged.json        合并后的完整数据集          （conform / targeted）
```

audit 模式只产出前 4 项，后 3 项不生成。

不要把中间产物散落在项目根目录或数据目录里。

## 运行环境

下文命令统一写作 `python`，但**在 Windows 上要先确认解释器**：`python` 常指向 WindowsApps 的占位 stub，它**静默失败**（exit 1、零输出），看不出是没装还是命令写错了。先探明再跑：

```powershell
Get-Command python, python3, py -ErrorAction SilentlyContinue | Select-Object Name, Source
py -V
```

可用的话一律改用 `py -X utf8`。`-X utf8` 是必需的——否则中文数据在 GBK 控制台会乱码，报告和 issue 描述都读不了。


## 流程

### Step 1 — 确认输入

需要拿到：目标数据文件、参考样例文件、可选的既有规则文档（很多项目已经有 `rule_description.md` 之类的字段规范，有就以它为准并补差，不要另起一套）。

用脚本或 `read_file` 采样看清数据形态，别急着全文读：条目总数、容器形式（数组 / JSONL / 对象映射）、字段出现频次。字段频次特别关键——出现 100/100 的是标准字段，出现 6/100 的往往是历史残留或某次实验留下的非标准字段。

### Step 2 — 提炼并校准 spec

读参考样例的**每一条**（参考样例通常只有几条，值得全读），提炼出 `spec.json` 和 `spec.md`。写法、支持的校验类型、以及如何区分「机械可校验」与「语义规则」，见 `references/spec-authoring.md`。可参照 `references/examples/word-roots.spec.json`（英语词根数据的完整示例）。

然后**必须校准**：

```bash
python <skill>/scripts/dataset_tool.py audit --data <参考样例> --spec spec.json
```

参考样例报出 error 时，**先判断是 spec 比样例严，还是样例本身有缺陷**（判据见「常见坑」第一条：结构性冲突 → 改规则；个例 → 改数据）。判定为 spec 过严就放宽约束或降级成 `"severity": "warn"`；判定为样例缺陷就把它记进待修清单，**不要顺手放宽规则**。两种情况都要在 `spec.md` 里写下判断和理由。这一步跳过或判反的代价是：后面几百条数据会被按错误标准"修坏"。

**退化情形：目标数据自身就是参考样例。** 这种情形常见于样例文件被注入 LLM prompt 作少样本范例（此时它既是规格来源，又是需要审的数据）。这时上面的校准是同义反复，必须改用其他真源：优先用既有规则文档（`rule_description.md` 之类）；若两者都没有，则无从校准，**先和用户确认规格再往下走**，不要凭数据现状反推规格。另外这类文件的质量门槛应严于普通条目——它的偏差会被模型复制到全量生成数据里。


### Step 3 — 全量体检

```bash
python <skill>/scripts/dataset_tool.py audit --data <数据> --spec spec.json --out audit.json --report audit.md
```

读 `audit.json` 的 `summary`，不要逐条读 `issues`（可能上万条）。然后做**总结性归纳**，这是你不可替代的价值：

- 按规则聚合：哪些是系统性问题，哪些是零散个例
- 判断根因：字段缺失是数据没写，还是 spec 定得过严？非标准字段是要删除，还是说明 spec 漏了一个合法可选字段？
- 机械校验查不到的语义问题：从 `spec.json` 的 `semanticRules` 出发核查（如词根归属是否真实、翻译是否忠实、explanation 能否推出 meaning）。**优先派并行子代理做全量语义审核，不要自己抽样**——子代理不只在 Step 5 修复阶段可用，audit 阶段同样适用：
  - 条目数少（≤20 条左右）：按条目切块，一个子代理审若干条，全量覆盖
  - 条目数多：先派子代理并行审一批（如 30~50 条）估算问题密度，再决定是否全量
  - 实测差距很大：某次 3 条目 / 24 例词的数据，自己顺读一遍查出 4 处，改成 3 个子代理并行全量审查出 15 处——漏掉的多是需要逐词核对词源和母语语感的问题（语素拼写立不住、前缀释义标错、中英字段义项不对等），抽样几乎必然漏整批
  - 给子代理的提示词里要写明：只审不改、逐项对照 `semanticRules` 的条号、拿不准的标「存疑」并说明理由、不要提纯风格偏好意见
- 给出修复优先级


audit 模式在此结束，把归纳写进 `report.md` 并向用户汇报。

### Step 4 — 分片

```bash
python <skill>/scripts/dataset_tool.py split --data <数据> --audit audit.json \
  --out-dir shards --size 8 --only-dirty
```

`--only-dirty` 只分片有问题的条目，干净条目原样保留，是省算力的关键。若要做语义级复核（机械校验发现不了的问题），去掉该参数处理全量。

`--size` 取决于单条数据的体积：条目大（如每条含 8 个例词、约 4KB）取 4~8；条目小（一行一个词条）可取 30~50。目标是单个分片连同 spec 一起塞进子代理上下文后仍有充足余量。

### Step 5 — 并行子代理修复

为每个分片派一个子代理。提示词模板、必须传给子代理的上下文、并发数、幂等与续跑、以及子代理最容易犯的错，全在 `references/agent-playbook.md`，派活前先读它。

三条底线要在每个子代理的提示词里写明：

- **最小改动**：只修 issues 列出的问题和明确违反语义规则的地方；无关字段、无关条目原样保留。数据是用户的资产，顺手"优化"文风等于制造无法审阅的 diff。
- **条目守恒**：分片进去 N 条，出来还是 N 条，`index` 与 id 不变，不许合并、拆分、删除、新增条目。
- **原样结构**：输出必须是完整条目，不能只输出改动的字段。

分片之间没有依赖，尽量一次派出多个子代理并行跑。

### Step 6 — 合并 + 守卫 + 复校

```bash
python <skill>/scripts/dataset_tool.py merge --data <数据> --fixed-dir fixed \
  --out merged.json --spec spec.json --report merge-report.md
python <skill>/scripts/dataset_tool.py audit --data merged.json --spec spec.json --out audit-after.json
python <skill>/scripts/dataset_tool.py diff --before <数据> --after merged.json --id-field id --out diff.md
```

`merge` 会拦住条目数变化、id 漂移、index 越界、分片缺失；`audit-after` 确认 error 数确实下降；`diff` 让改动可审阅。

如果复校后 error 没降或反而上升，不要靠再跑一轮子代理去"盖住"问题——先读 diff 找出子代理误解了什么，回头修 spec 或提示词。同一处反复失败两次以上，说明规格本身有歧义。

### Step 7 — 写回

**不要擅自覆盖原数据文件。** 默认交付 `merged.json` + 报告，让用户确认后再替换；用户明确要求原地写回时，先备份（`<name>.bak-run-N.json`），并保持原文件的缩进与换行风格（`merge --newline keep` 默认已处理，Windows 项目的 CRLF 尤其容易被写坏）。

## 报告结构

`report.md` 用这个结构，让人 30 秒能看懂发生了什么：

```markdown
# <数据集名> 对齐报告（run-N）

## 结论
一句话：处理了多少条，修了什么，还剩什么问题。

## 规格来源
参考样例路径 + 既有规则文档 + spec 校准时做的放宽决定及理由。

## 体检结果
按规则聚合的问题分布（修复前 → 修复后），系统性问题与个例分开列。

## 变更摘要
涉及条目数、涉及字段路径 Top N、典型 before/after 各 1~2 例。

## 未处理与风险
需要人工决策的项、超出参考样例覆盖范围因而无从判断的项、语义审核的覆盖范围（全量还是抽样）与残余问题密度估计。

```

## 常见坑

- **参考样例与规则文档冲突时，先判断是谁错**——不要默认样例胜出。判据是冲突的**分布形态**：
  - **结构性**（同类条目全都无法满足）→ 规则错，改规则。例：规范要求 `breakdown.root` 必须是 root 字段的变体之一，但词根为 `a-/an-` 的**词缀类条目 8/8 全部违反**——这类条目的语素必然落在 `breakdown.prefix`，规则漏了一类数据形态，应补例外条款。
  - **个例**（只有个别条目不满足）→ 样例错，改数据。例：同一份样例里 `simple` 拆成 `sim + ple` 而 root 字段是 `plic/plex/ply`（1/8），`conspicuous` 用了未声明的变体 `spic`（1/8）——这是选词和字段维护的缺陷，不是规则太严。
  把个例当成"规则是软约束"的证据，会把数据缺陷固化进 spec，后续几百条数据都按错误标准对齐。降级为 warn 只是让流程能往下走的临时手段，不等于结论。

- **非标准字段的处置需要用户拍板**：少数条目独有的额外字段（`memoryHint`、`literalMeaning`……）可能是有价值的增量内容，也可能是脏数据。删除是不可逆的，问一句再动手，别默认删。
- **"补全"不等于"编造"**：先确认资源是否真实存在；无法核实的内容宁可留空并在报告里列出，也不要生成看起来合理的假数据。
- **补全数量类约束**（如例词补到 8 个）时，新增内容的质量标准和存量一致，且必须真实属于该条目所属范畴——凑数比缺项更糟。
- **替换或新增样本时，典型性不得低于存量**：修掉一个不合规的样本，最省事的做法是找一个"技术上合规"的冷僻替代品——格式过了，数据集却变得没人用得上。替代品必须和被它换掉的东西处在同一可及性档位：常用度、篇幅、复杂度都不能明显退化。判据要落到数据集的受众上（面向初学者的词表不该塞专业术语，面向大众的商品目录不该换成小众型号），并优先拿项目里现成的分级资源核验（词频表、分级词书、销量榜之类），不要凭感觉。宁可多花力气找一个既合规又常用的替代品，也不要交一个没人认得的样本。

- **新增条目属于扩充数据集，不是对齐**：除非用户明确要求，不要增加条目总数。
